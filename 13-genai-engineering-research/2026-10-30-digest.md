## The common lesson

An agent is an LLM placed inside a control loop:

```text
task -> choose action -> call tool -> observe result -> choose next action -> finish
```

The model proposes actions. Python owns the state, tool permissions, retries, limits, and tests. In MuleSoft terms, the model resembles a fallible dynamic router; the surrounding application remains the flow engine, policy layer, audit trail, and error handler.

## 1. Developers as Managers of AI Agents: A Workplace Shadowing Study

- **Primary source:** [arXiv:2610.33588](https://arxiv.org/abs/2610.33588)
- **Published:** 24 October 2026
- **Evidence type:** workplace observation of 11 professional developers, about 15 hours of shadowing, 255 prompts, and 4.6 hours of follow-up interviews.
- **Finding:** developers spent an average of **33.4% of observed time** writing prompts or checking AI responses. The researchers observed three working patterns: **Supervisor** (inspect the artifact), **Delegator** (coordinate and delegate implementation/checking), and **Learner** (use the agent to understand the problem).
- **Evidence boundary:** this is a small observational study. It describes what these developers did; it does not prove that one pattern causes higher productivity.

### Core concept, from zero: agent supervision

A coding agent can read files, run commands, edit code, and inspect test output. It still lacks the business context and authority that a human developer has. **Supervision** means deciding what work to delegate, supplying missing context, and verifying the result before accepting it.

**Prerequisite:** understand a normal Python function call and its input/output. A tool is often just a function made available to the model with a name, description, and argument schema.

**API/MuleSoft analogy:** assigning an agent “add an endpoint” is like invoking a composite integration flow. You do not validate the flow merely because every connector returned HTTP 200. You inspect whether the correct systems were called, transformations respected the contract, and the business outcome occurred.

### Why it matters

Agent productivity is partly a human workflow design problem. If you run several tasks in parallel without explicit acceptance criteria, attention becomes the bottleneck. A polished final answer can also hide a wrong intermediate action.

For a beginning GenAI engineer, this is a reason to start with one visible workflow and a trace before building a multi-agent team.

### Project connection

Add a simple trace to the Enterprise Document Assistant's retrieval flow:

```text
question
  -> retrieve passages
  -> check whether evidence is sufficient
  -> answer with citations OR request human review
```

Keep these fields in Python state:

```python
state = {
    "question": "What is the Tier B transfer limit?",
    "retrieved_ids": [],
    "decision": None,
    "answer": None,
    "needs_review": False,
}
```

This can later become LangGraph state, but a dictionary and ordinary functions are enough to learn the idea.

### Small implementation

```python
from dataclasses import dataclass, field

@dataclass
class Trace:
    events: list[dict] = field(default_factory=list)

    def record(self, step: str, **data) -> None:
        self.events.append({"step": step, **data})

def answer_flow(question: str, search, generate) -> tuple[str, Trace]:
    trace = Trace()
    hits = search(question)
    trace.record("retrieve", hit_ids=[h["id"] for h in hits])

    if not hits or hits[0]["score"] < 0.70:
        trace.record("route", outcome="human_review")
        return "I need a reviewer because the evidence is weak.", trace

    answer = generate(question, hits)
    trace.record("generate", cited_ids=answer["cited_ids"])
    return answer["text"], trace
```

**Expected output for a weak search result:**

```text
I need a reviewer because the evidence is weak.
[
  {"step": "retrieve", "hit_ids": ["policy-7"]},
  {"step": "route", "outcome": "human_review"}
]
```

The threshold is a project hypothesis, not a universal truth. Tune it with labeled examples.

### One measurable experiment

Prepare 20 questions: 10 answerable from your sample policies and 10 deliberately unanswerable.

Compare:

1. always generate an answer;
2. route to review when top retrieval score is below a threshold.

Measure:

- **unsupported-answer rate:** answers without supporting policy text / generated answers;
- **review rate:** review decisions / all questions;
- median time spent checking each run.

**Success target for the lab:** reduce unsupported answers by at least 50% without routing more than 40% of answerable questions to review.

### Design choices and trade-offs

- **One agent vs several:** one agent is easier to trace and debug; separate researcher and reviewer agents may improve separation of duties but add cost and coordination failures.
- **Free-form delegation vs acceptance criteria:** free-form prompts are faster to write; explicit input, output, constraints, and tests reduce ambiguity.
- **Full transcript vs structured trace:** transcripts help debugging but are noisy and may contain secrets. Structured events are easier to query and redact.
- **Human review everywhere vs risk-based review:** universal review is safer but expensive. Route only low-confidence or high-impact cases once evaluation supports the policy.

### Common mistakes and debugging

- **Mistake:** judging only the final prose.  
  **Debug:** inspect retrieved IDs, tool arguments, errors, retries, and citations.
- **Mistake:** starting three agents before one workflow is reliable.  
  **Debug:** make one deterministic path pass a labeled test set first.
- **Mistake:** trusting an arbitrary confidence score.  
  **Debug:** plot errors by score on your own data and choose a threshold from observed results.
- **Mistake:** logging raw documents or credentials.  
  **Debug:** log IDs, timing, status, and redacted summaries.

### Interview takeaway

**Beginner answer:** “An agent is a loop that lets an LLM choose actions and use tools. I keep execution and state in code, record every step, and send weak-evidence cases to review.”

**Senior extension:** “I define acceptance criteria and trace intermediate actions because task success alone can hide bad tool use. I measure unsupported answers, review rate, latency, and human attention, then use those results to decide which steps can be autonomous.”

**Follow-up: Why not use LangGraph immediately?**  
Use plain Python first so the state transitions are visible. LangGraph becomes useful when the flow needs durable state, branching, retries, pauses, or resumability. A framework does not remove the need to define those transitions.

**Practice task:** implement the trace and weak-evidence route, run all 20 questions, and save a CSV with question, expected answerability, top score, route, citations, and correctness.

## 2. InfraDev: Can Coding Agents Develop AI Infrastructure, and How Can We Tell?

- **Primary source:** [arXiv:2610.36589](https://arxiv.org/abs/2610.36589)
- **Published:** 27 October 2026
- **Evidence type:** a 36-task benchmark built from real merged pull requests in Megatron-LM, vLLM, and verl, evaluated across six frontier models.
- **Finding:** the best model resolved **38.9%** of tasks. Added hidden probes rejected **32%** of submissions that passed the official tests. Fewer than 2% of assertions written by agents checked resource requirements such as memory, time, or network traffic. A reusable skill based on observed failure modes improved one model by **10.5 percentage points** on Megatron-LM tasks.
- **Evidence boundary:** these are difficult multi-GPU infrastructure tasks. The exact success rates should not be generalized to a FastAPI/RAG application, but the verification failure pattern is directly useful.

### Core concept, from zero: test the requirement, not just the output

A normal unit test may confirm that a function returns the expected answer once. A system can pass that test while violating another promise: it leaks state between calls, makes excessive API requests, is too slow, or uses too much memory.

A **hidden probe** is an evaluator-owned test that checks requirements the implementation cannot simply tailor itself to. An **adversarial patch** is a deliberately wrong implementation that passes the existing tests; it demonstrates a hole in the test suite.

**Prerequisite:** know the difference between:

- **functional correctness:** did it return the right answer?
- **state/lifecycle correctness:** does it remain right across repeated calls, resets, and failures?
- **behavioral requirement:** did it also meet latency, memory, traffic, permission, or cost limits?

**API/MuleSoft analogy:** an API may return the correct payload while calling Salesforce 100 times, losing the correlation ID, or reusing one tenant's cached token for another. Contract tests alone would miss these lifecycle and non-functional failures.

### Why it matters

RAG and agent systems have the same layered correctness problem:

- retrieval can find the wrong passages while the answer sounds good;
- cached state can leak between users;
- retries can duplicate tool side effects;
- an agent can reach the answer using too many calls;
- a coding agent can write tests that merely confirm its own implementation.

Verification should therefore include independent examples and resource limits.

### Project connection

For the Enterprise Document Assistant, turn each product promise into a probe:

| Promise | Probe |
|---|---|
| answers cite retrieved evidence | every factual sentence maps to a retrieved chunk ID |
| tenant isolation | tenant A can never retrieve tenant B chunks |
| retry safety | repeated request ID creates no duplicate side effect |
| bounded tool use | no more than 3 retrieval/tool calls per question |
| acceptable speed | p95 latency stays below the lab target |
| clean state | asking question B after A gives the same result as B in a fresh process |

This is the bridge from a demo to an enterprise GenAI service.

### Small implementation

```python
from time import perf_counter

def evaluate_case(flow, case):
    started = perf_counter()
    result = flow(
        question=case["question"],
        tenant_id=case["tenant_id"],
        request_id=case["request_id"],
    )
    latency_ms = (perf_counter() - started) * 1000

    assert set(result["source_tenants"]) == {case["tenant_id"]}
    assert result["tool_calls"] <= 3
    assert latency_ms < 500
    if case["answerable"]:
        assert case["required_source_id"] in result["cited_ids"]
    else:
        assert result["needs_review"] is True

    return {
        "passed": True,
        "latency_ms": round(latency_ms, 1),
        "tool_calls": result["tool_calls"],
    }
```

**Expected output:**

```python
{"passed": True, "latency_ms": 84.6, "tool_calls": 1}
```

The 500 ms and 3-call limits are lab targets. Production targets must come from user needs, model latency, and cost budgets.

### One measurable experiment

Create 15 evaluation cases:

- 5 normal answerable questions;
- 5 unanswerable questions;
- 5 boundary cases: repeated request, tenant isolation, empty index, tool timeout, and question-order state leakage.

Run them first with only answer-correctness checks, then with the full probes.

Measure:

- **false-pass rate:** faulty runs accepted by the basic tests / all faulty runs;
- p95 latency;
- average tool calls;
- tenant leakage count;
- unsupported-answer count.

Inject at least three deliberate faults, such as removing the tenant filter, disabling the call limit, and retaining previous retrieved passages. The experiment succeeds when the full probes catch all three and the basic suite misses at least one; that shows the probes add information.

### Design choices and trade-offs

- **Public tests vs hidden probes:** public tests guide implementation; independent probes resist overfitting. Requirements must still be stated clearly so evaluation is fair.
- **LLM judge vs deterministic assertions:** an LLM judge can assess meaning but is variable and costly. Use code for IDs, counts, permissions, schema, and latency; reserve model grading for semantic qualities.
- **Exact thresholds vs distributions:** a single latency threshold is simple but brittle. Track p50/p95 and compare versions under the same environment.
- **Agent-written tests vs evaluator tests:** agent tests give fast feedback; an independent suite prevents the implementer from defining success around its own patch.

### Common mistakes and debugging

- **Mistake:** one golden-path test.  
  **Debug:** add repeated calls, reordered calls, timeouts, empty results, and tenant boundaries.
- **Mistake:** evaluating answer quality before retrieval.  
  **Debug:** first measure whether the required chunk appears in top-k; then judge the generated answer.
- **Mistake:** using an LLM judge for facts code can verify.  
  **Debug:** assert schemas, source IDs, permissions, call counts, and budgets deterministically.
- **Mistake:** accepting the agent's own tests as independent evidence.  
  **Debug:** maintain a reviewer-owned evaluation set and inject known faults.

### Interview takeaway

**Beginner answer:** “Passing unit tests is insufficient for an agent. I separately test the returned answer, state across calls, permissions, tool-call count, and latency.”

**Senior extension:** “I derive probes from explicit service promises and validate that each probe accepts a known-good implementation and rejects deliberately faulty ones. I keep deterministic checks for contracts and budgets, semantic grading for qualities that require judgment, and I report false-pass rate alongside task success.”

**Follow-up: What is the RAG equivalent of a coding patch that passes tests but is still wrong?**  
An answer may match the reference wording while its cited passage does not support it, or retrieval may cross a tenant boundary. Measure retrieval relevance and authorization before answer similarity.

**Practice task:** add the 15-case evaluator to the project, inject the three faults, and record which suite catches each fault.

## Five-minute interview recap

- An agent is a model inside a controlled action/observation loop.
- The application, not the model, owns permission, state, retries, budgets, and audit.
- Final-answer quality does not reveal whether the workflow used tools safely or efficiently.
- Test retrieval separately from generation.
- Test repeated calls and lifecycle state, not only a single invocation.
- Use independent probes and deliberate faults to estimate false passes.
- Start with a deterministic Python workflow; adopt LangGraph when explicit graph state and recovery solve a real need.
