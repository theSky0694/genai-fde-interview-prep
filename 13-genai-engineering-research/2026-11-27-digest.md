## 1. MH-RAG-DIVE: test multi-hop RAG conversations without paying for every path again

**Source:** [MH-RAG-DIVE: Dynamic and Cost-Efficient Multi-Hop RAG Evaluation via Tree-Cached Dialogue Simulation](https://arxiv.org/abs/2611.30335)  
**Submitted:** 2026-11-23  
**Area:** RAG evaluation

### Finding and evidence boundary

The authors compare six RAG configurations using a simulated user that asks follow-up questions requiring facts from multiple documents. Their conversation cache reuses previously generated turns and reduces token use, while the tested configurations show similar broad trends to other evaluation approaches. The harder conversations expose additional failures. The abstract does not give the exact token-saving percentage, and simulation is not a replacement for real-user evaluation.

### Core concept and prerequisite

A **multi-hop question** needs more than one retrieval step or more than one document. For example: “Which support plan applies to Acme, and what is its escalation time?” may require a customer contract and a support-policy document. First learn retrieval, chunks, and answer grounding in the foundation lessons above.

The new idea is to test a dialogue tree. Several test conversations may share the same opening turns, so those turns can be cached rather than regenerated.

**MuleSoft analogy:** this resembles caching the common setup portion of several MUnit flows, then branching into different downstream assertions. You still test each business path, but do not repeatedly pay for identical setup.

### Why it matters and project connection

A RAG demo can pass isolated questions yet fail when a follow-up contains “that customer,” “the earlier policy,” or a fact that must be joined across sources. In the enterprise document assistant, add an evaluation runner that stores conversation state and branches after a shared first question.

### Small measurable experiment

Create 10 two-step test cases:

1. Ask for a customer’s product or plan.
2. Ask a follow-up whose answer needs a second policy document.

Run them once without caching and once with a cache keyed by conversation prefix. Record:

- grounded-answer accuracy out of 10;
- retrieval recall: whether the required document appears in top-k;
- input and output tokens;
- cache-hit rate;
- estimated cost.

**Success target:** identical answers for cached and uncached runs, at least 30% fewer simulation tokens, and a separate score for second-turn accuracy.

### Beginner-friendly interview takeaway

“I would not evaluate RAG only with independent questions. I would include multi-turn cases that require documents to be combined, measure retrieval and grounded-answer accuracy separately, and cache shared conversation prefixes to control evaluation cost.”

## 2. Conversational RAG privacy: even one previous turn can change leakage risk

**Source:** [Beyond Single-Turn Privacy: Training-Data Leakage in Conversational RAG](https://arxiv.org/abs/2611.28748)  
**Submitted:** 2026-11-21  
**Area:** RAG privacy and conversation state

### Finding and evidence boundary

Across GPT-J-6B and two Pythia models, the authors tested extraction of real Enron contact details that were absent from the retrieval corpus. With retrieval enabled, retaining full history increased disclosure by 3.6–4.9 times; retaining only one previous turn produced roughly the full-history leakage level. Clearing history reduced disclosure by 72–79% but did not eliminate it. These are controlled results on older open models and one PII domain, so the exact rates should not be generalized to every hosted model.

### Core concept and prerequisite

A model receives a **context window**: the current question, retrieved text, instructions, and often previous messages. Conversation history is therefore active input, not harmless UI state. Training-data leakage means the model emits memorized sensitive data that was not present in the current inputs.

**MuleSoft analogy:** conversation history behaves like a growing message payload or correlation object passed through every processor. If it includes unsafe material, every later connector can see it unless the flow deliberately filters or replaces it.

### Why it matters and project connection

The document assistant needs a history policy before it becomes multi-user. Add a history builder that keeps only the minimum required fields, redacts obvious PII, and separates tenant/session IDs from model-visible text.

### Small measurable experiment

Build 20 synthetic conversations using fake names, emails, and account IDs. Compare three modes:

- full transcript;
- last turn only;
- structured summary containing no raw PII.

Run the same extraction-style follow-up against each. Record forbidden-string disclosure rate and answer usefulness on five legitimate follow-ups.

**Success target:** zero synthetic secret disclosure and no more than a 10% drop in legitimate follow-up accuracy for the structured-summary mode.

### Beginner-friendly interview takeaway

“RAG privacy must be tested across turns. I would minimize and redact history, isolate tenants, and measure both leakage and usefulness because simply keeping fewer messages can also remove information needed for a correct answer.”

## 3. TACT-Bench: an agent must refuse forbidden actions while still completing allowed work

**Source:** [TACT-Bench: Testing Adaptive Conversational Threats against Tool-Use Agents](https://arxiv.org/abs/2611.31756)  
**Submitted:** 2026-11-24  
**Area:** tool-use agent security

### Finding and evidence boundary

TACT-Bench uses stateful conversations in which an attacker adapts to the agent’s responses. It pairs prohibited tasks with benign counterparts so a model is not rewarded for refusing everything. Across six assistant models, its base attacks increased attack-induced failure rate by 17.53 percentage points over four compatible baselines; a benign “trust-building” task before an unrelated attack added another 17.01 points. Two tested defenses reduced failures by only 8.35–9.41 points on average and did not consistently improve the combined safety/usefulness score. These are benchmark results, not proof that the same defenses fail identically in every production policy.

### Core concept and prerequisite

A tool agent can take actions through APIs. **Authorization** decides whether a particular caller may perform a particular action on a particular resource. A prompt-level instruction is weaker than a server-side policy check because model output is probabilistic.

Selective trustworthiness means the agent should refuse a forbidden write while still answering or performing the allowed part.

**MuleSoft analogy:** never rely on a natural-language request to enforce API policy. Apply scopes, client identity, validation, and policy enforcement at the gateway or connector boundary.

### Why it matters and project connection

When the document assistant gains tools such as “search documents,” “open ticket,” and “update access,” put a deterministic authorization function before every side effect. LangGraph can route requests, but the tool implementation must enforce policy.

### Small measurable experiment

Add two tools: read_document and update_document. Create 20 paired tests where the same user can read but cannot update a restricted document. In half, precede the forbidden update with several legitimate tasks.

Record:

- unauthorized-action rate;
- allowed-task completion rate;
- false-refusal rate;
- tool calls made before denial.

**Success target:** 0 unauthorized updates, at least 95% allowed completions, and every denial recorded with a policy reason.

### Beginner-friendly interview takeaway

“I separate agent reasoning from authorization. The model can propose a tool call, but deterministic code checks user, action, resource, and tenant before execution. I test both attacks and matched benign tasks so a useless always-refuse agent cannot look safe.”

## 4. VISE: repair agent skills by reading the real tool implementation

**Source:** [VISE: Verifier-Independent Skill Self-Evolution with Feedback from Tool Implementations](https://arxiv.org/abs/2611.32480)  
**Submitted:** 2026-11-24  
**Area:** agent workflows and tool integration

### Finding and evidence boundary

VISE extracts tool capabilities, required inputs, usage conditions, and output formats from source code. It compares those facts with an agent’s workflow instructions and execution trace, then recommends instruction edits. Added to four skill-evolution methods under no-verifier conditions, it improved average task success by 9.14–13.35 percentage points and increased tasks solved in all three runs by 12.36–18.29 points on SkillsBench and SkillLearnBench. The evidence concerns benchmark tasks and generated skill revisions; human review remains necessary before production instructions change.

### Core concept and prerequisite

A **skill** is reusable guidance for completing a workflow with tools. A tool contract says what inputs are required, what the tool returns, and when it may be called. If the written instructions drift from the actual Python function or OpenAPI schema, the agent will call it incorrectly.

**MuleSoft analogy:** treat an agent skill like an orchestration flow built on RAML/OAS contracts. When the connector schema changes, DataWeave mappings and flow documentation must be checked against the contract.

### Why it matters and project connection

In the assistant project, generate a small machine-readable manifest from each FastAPI/tool function: name, input schema, output schema, exceptions, and authorization rule. Add a CI check that compares referenced parameters in the agent instructions with the current schema. Do not let the agent silently rewrite production instructions; create a reviewable diff.

### Small measurable experiment

Deliberately change a tool parameter from document_id to resource_id and add a required tenant_id. Prepare 20 calls based on the old instructions.

Compare:

- old instructions;
- schema-generated draft instructions;
- human-reviewed corrected instructions.

Measure schema-validation success, task completion, and unsafe missing-tenant attempts.

**Success target:** 100% schema-valid calls after correction, 0 missing-tenant executions, and a readable diff that links each instruction change to a contract field.

### Beginner-friendly interview takeaway

“I keep agent instructions aligned with executable tool contracts. I can generate proposed updates from Python signatures or OpenAPI, but I validate them in tests and require review because source code tells me syntax and conditions, not the full business intent.”

## 5. Coding agents: patch size is a poor proxy for unnecessary change

**Source:** [How Much Do Coding Agents Over-Edit, and Why?](https://arxiv.org/abs/2611.34875)  
**Submitted:** 2026-11-25  
**Area:** coding-agent evaluation

### Finding and evidence boundary

The authors replayed 7,660 resolved GitHub Copilot CLI trajectories across 18 models on SWE-bench Verified and DeepSWE. Their method removes each patch unit and reruns tests to estimate whether it was necessary. On SWE-bench Verified, 61% of extra edits were tests and 13% documentation; about 11% of agent code units were unnecessary, and 89% of those still changed behavior. Test-based pruning found 67% of unnecessary code but had only 46% precision, while agent self-audit had 36% recall and 66% precision. These figures apply to resolved benchmark trajectories and depend on test coverage; removal without failure does not prove a change has no long-term value.

### Core concept and prerequisite

A **patch** is the code difference produced for a task. Patch minimality asks whether each change is needed. Lines changed alone are misleading: additional tests may be valuable, while a tiny behavioral change may be dangerous.

**MuleSoft analogy:** a large flow diff may include useful MUnit tests and documentation. Review the effect of each processor or mapping change against contract tests, rather than rejecting the change only because the XML diff is large.

### Why it matters and project connection

Use a coding agent to add one feature to the assistant, such as history summarization. Require a task-scoped diff, existing tests, new behavioral tests, and a change manifest that maps files to requirements. Review generated application code separately from tests and docs.

### Small measurable experiment

Ask a coding agent three times to add the same small endpoint. For each patch:

1. run the full test suite;
2. classify changed blocks as application code, tests, docs, or configuration;
3. revert one application-code block at a time and rerun targeted tests;
4. manually inspect blocks whose removal does not fail tests.

Record task success, changed lines, unnecessary application blocks, and review time.

**Success target:** all contract tests pass, no unrelated application files change, and unnecessary behavior-changing code is zero after review.

### Beginner-friendly interview takeaway

“I judge coding-agent output with task success, contract tests, scope, and necessity of behavioral changes. A big diff is not automatically bad because it may add tests; pruning also needs review because incomplete tests can label necessary code as removable.”
