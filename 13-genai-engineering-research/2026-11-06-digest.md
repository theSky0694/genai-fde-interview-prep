## 1. EAGR: Evidence-Guided Adaptive Graph Retrieval

- **Primary source:** [arXiv:2611.01910](https://arxiv.org/abs/2611.01910)
- **Submitted:** 1 November 2026
- **Area:** multi-step RAG
- **Author-reported finding:** averaged across HotpotQA, 2WikiMultiHopQA and MuSiQue, EAGR improved answer accuracy by 17 percentage points over the authors' vanilla-RAG baseline and by 4 points over their strongest graph-aware baseline.
- **Evidence boundary:** these are public question-answering benchmarks. They do not prove the same improvement on bank policies, and an LLM participates in deciding what evidence to explore.

### Core concept and prerequisite

**Prerequisite:** understand basic RAG: retrieve a few text chunks, add them to the prompt, and ask the LLM to answer from them. See sections 3–8 of [concept foundations](../00-genai-concept-foundations.md).

Basic RAG searches once using the user's original question. That can fail when the answer requires a chain:

1. find policy A;
2. discover that policy A refers to customer tier B;
3. follow tier B to a separate limits table;
4. combine both pieces.

This is called **multi-hop retrieval**: one retrieved fact tells you what to retrieve next.

EAGR starts with semantically similar passages, reads compact metadata attached to them, and explores related passages until it judges the evidence sufficient. It treats those relationships as an implicit graph stored in normal vector-database metadata rather than requiring a separate graph database.

**MuleSoft analogy:** a single RAG search resembles one connector call. Adaptive retrieval resembles orchestration where the first response contains a key needed for the second request. You do not call every downstream system in advance; each response determines the next lookup.

### Why it matters

Enterprise questions often cross documents: an eligibility rule in one PDF, a product code in another, and a limit in a table. Increasing top-k can add noise and cost without following the correct relationship. Adaptive retrieval makes the next lookup depend on evidence already collected.

The design also shows that graph-style navigation does not automatically require Neo4j. Metadata relationships inside the existing index may be enough for a smaller project.

### Project connection

Extend the document assistant's chunk metadata:

```python
chunks = [
    {
        "id": "eligibility-12",
        "text": "Tier B customers use transfer schedule TS-7.",
        "links": ["schedule-TS-7"],
    },
    {
        "id": "schedule-TS-7",
        "text": "TS-7 daily transfer limit is ₹75,000.",
        "links": [],
    },
]
```

A simple learning version:

```python
def adaptive_retrieve(question, vector_search, by_id, max_hops=2):
    evidence = vector_search(question, top_k=2)
    seen = {item["id"] for item in evidence}

    for _ in range(max_hops):
        new_items = []
        for item in evidence:
            for linked_id in item.get("links", []):
                if linked_id not in seen:
                    new_items.append(by_id(linked_id))
                    seen.add(linked_id)
        if not new_items:
            break
        evidence.extend(new_items)

    return evidence
```

**Expected result:** a question about the Tier B transfer limit initially retrieves `eligibility-12`, then follows `schedule-TS-7`, providing the amount and the rule connecting it to Tier B.

This code teaches the data flow; it is not the paper's algorithm.

### Small measurable experiment

Create 20 synthetic questions:

- 10 answerable from one chunk;
- 10 requiring two linked chunks.

Compare:

1. single vector search with top-k 4;
2. top-k 2 plus at most two metadata hops.

Measure:

- evidence recall: required chunks retrieved / required chunks;
- irrelevant chunks per question;
- retrieval latency;
- total context tokens;
- answer correctness.

**Useful success condition:** improve recall on two-hop questions without increasing average context tokens by more than 25%.

### Beginner interview takeaway

“Normal RAG searches once. Multi-hop RAG uses one retrieved fact to decide the next retrieval. I would begin with explicit document links in vector-store metadata, bound the number of hops, keep source IDs, and compare evidence recall, latency and context size against single-shot retrieval.”

## 2. Boundary Contracts for Coding-Agent Autonomy

- **Primary source:** [arXiv:2611.01265](https://arxiv.org/abs/2611.01265)
- **Submitted:** 31 October 2026
- **Area:** coding-agent authority
- **Author-reported finding:** on 40 tasks from one enterprise repository, adding explicit artifact roles raised strictly acceptable patches from 9 to 18. Edit-selection F1 increased from 0.440 to 0.682.
- **Evidence boundary:** this is a small pilot using one repository and agent setup. The authors explicitly say it does not establish general effectiveness.

### Core concept and prerequisite

**Prerequisite:** understand that a coding agent can search, read, edit and test repository files.

Finding a relevant file does not mean the agent should edit it. The paper assigns task-specific roles:

- **editable:** may be changed;
- **inspect-only:** may be read for understanding but preserved;
- **required:** must be considered or changed for completion;
- **protected:** must remain unchanged.

A **boundary contract** is a machine-readable statement of these roles before the agent starts.

**MuleSoft analogy:** an integration user may have read access to customer data, write access to cases, and no access to payment configuration. Relevance to the flow does not grant write permission. Coding-agent file access needs a similarly explicit operational scope.

### Why it matters

Prompts such as “only modify these files” are guidance. A boundary checked by the execution layer can become enforcement. This distinction matters for shared libraries, API contracts, deployment files, generated artifacts and regulated code.

The deeper lesson applies to tool agents too: “the agent can discover this resource” and “the agent may mutate this resource” are separate decisions.

### Project connection

Add a boundary contract for an agent improving the document assistant:

```python
BOUNDARY = {
    "app/retrieval.py": "editable",
    "tests/test_retrieval.py": "required",
    "app/auth.py": "inspect_only",
    "config/production.env": "protected",
}

def can_edit(path: str) -> bool:
    return BOUNDARY.get(path) in {"editable", "required"}

def write_file(path: str, content: str) -> None:
    if not can_edit(path):
        raise PermissionError(f"Agent may not edit {path}")
    # perform the write in the sandbox
```

**Expected behavior:**

```text
write app/retrieval.py       -> allowed
write tests/test_retrieval.py -> allowed
write app/auth.py            -> blocked
write config/production.env  -> blocked
```

For a real repository, generate a proposed contract, review it before execution, and enforce it in the file tool or sandbox rather than trusting the model to remember it.

### Small measurable experiment

Give the same coding task to an agent twice:

1. ordinary task prompt;
2. task prompt plus enforced boundary contract.

Inject four protected or inspect-only files that appear relevant.

Measure:

- protected-file edit attempts;
- required files touched;
- tests passed;
- acceptable patch rate under a human-written rubric;
- additional prompt tokens and review time.

**Success condition:** zero successful protected writes while retaining all required changes and tests.

### Beginner interview takeaway

“Repository context tells an agent what may be relevant; a boundary contract tells it what it may or must do. I would represent editable, inspect-only, required and protected files explicitly, have a human review the scope, and enforce it in the file tool. Prompt instructions alone are not an authorization control.”

## 3. Getting a Grip: Governed Messages for Human–Agent Software Teams

- **Primary source:** [arXiv:2611.00689](https://arxiv.org/abs/2611.00689)
- **Submitted:** 31 October 2026
- **Area:** multi-agent workflow governance
- **Evidence:** 926 controlled runs, of which 899 were analyzable, plus a four-week field study involving up to 19 agents and two people.
- **Author-reported finding:** changing which messages could start work, together with limits on repeats, was associated with a coordination-failure drop from 42% to 13%. The adjusted significance value across nine registered tests was 0.057, so treat the result as suggestive. Roles and voting instructions alone did not reliably enforce the intended process.

### Core concept and prerequisite

**Prerequisite:** understand an agent workflow as messages plus state: a requester gives a task, an agent acts, another agent or human reviews, and the system records the result.

The paper's main idea is **governed messaging**. Messages have types, senders, recipients and effects. Only particular message types from authorized principals can start work or approve a decision.

A plain chat says:

```text
“Please deploy this.”
```

A governed message resembles:

```json
{
  "type": "approval",
  "actor": "human:release-manager",
  "target": "deploy:build-184",
  "decision": "approved",
  "event_id": "evt-901"
}
```

**MuleSoft analogy:** an email saying “go ahead” is not the same as an authenticated approval event in an API-led flow. Enterprise integration already separates message payload, identity, schema, routing and audit. Multi-agent systems need the same discipline.

### Why it matters

Adding agents multiplies communication paths. Natural-language roles such as “you are the reviewer” are not reliable access control. Typed messages give the application something deterministic to validate, route, deduplicate and audit.

The field study also found that human approvals became the slow resource. Therefore, measure reviewer queue time rather than assuming more agents improve throughput.

### Project connection

For the document assistant, use typed events for escalation and approval:

```python
from typing import Literal, TypedDict

class WorkflowEvent(TypedDict):
    type: Literal["evidence_ready", "review_requested", "approved", "rejected"]
    actor: str
    request_id: str
    evidence_ids: list[str]

def may_finalize(event: WorkflowEvent) -> bool:
    return (
        event["type"] == "approved"
        and event["actor"].startswith("human:")
        and bool(event["evidence_ids"])
    )
```

**Expected behavior:** an agent-generated `approved` event is rejected; an authenticated human approval with evidence IDs permits finalization.

In LangGraph, events update state and deterministic conditional edges decide the next node.

### Small measurable experiment

Simulate 30 workflows with:

1. free-text coordination;
2. typed events, actor checks, duplicate-event rejection and a bounded retry policy.

Inject:

- repeated requests;
- an agent pretending to approve;
- a missing evidence ID;
- two conflicting decisions.

Measure:

- unauthorized transitions;
- duplicate work;
- completed workflows;
- human approval wait time;
- event-log completeness.

**Success condition:** typed governance blocks every unauthorized approval and duplicate start, while the audit log reconstructs who caused each transition.

### Beginner interview takeaway

“In a multi-agent system, I would not treat every chat message as a command. I use typed events with authenticated actors, allowed transitions, idempotency and an append-only audit record. The model can propose work, but code decides which message starts work or approves a consequential action.”

## 4. Trace2Eval: Evaluation from Real Coding-Agent Traces

- **Primary source:** [arXiv:2611.06506](https://arxiv.org/abs/2611.06506)
- **Submitted:** 4 November 2026
- **Area:** coding-agent evaluation
- **Evidence:** approximately 20,000 anonymized online traces were sampled; 14,603 were classified as code-related, and the final benchmark contained 129 tasks reconstructed with their starting workspace and environment.
- **Author-reported finding:** rubric-guided revisions gained 10.05 percentage points on average across 19 model/harness configurations. The rubric uses source and runtime evidence and is aligned with human judgments.
- **Evidence boundary:** reconstructing a user's original workspace from traces can be imperfect. Rubric and judge calibration reduce this risk but do not eliminate it.

### Core concept and prerequisite

**Prerequisite:** understand an evaluation case as an input, expected behavior and measurable checks.

A static coding benchmark often says, “fix this issue in this repository snapshot.” Real users also ask for small web apps, integrations, configuration, refactoring and incomplete requirements. Trace2Eval tries to build test tasks from real interaction histories and restore the files and dependencies that existed before the agent worked.

A **rubric** is a list of explicit scoring criteria. For example:

- the endpoint works;
- unauthorized users receive 403;
- citations appear;
- the UI exposes the feature;
- tests pass;
- no protected file changes.

**MuleSoft analogy:** a unit test for one DataWeave mapping cannot evaluate an entire customer onboarding flow. You need the original environment and an acceptance rubric covering the actual business journey.

### Why it matters

Benchmarks shape what teams optimize. If the test set contains only bug fixes, an agent may score well while failing common integration work. Evaluation should reflect your own users, starting files, deployment constraints and definition of done.

The paper also supports a practical loop: evaluation feedback should name a verifiable defect, then the agent revises the artifact and the same rubric rechecks it.

### Project connection

Convert actual development tasks from the document assistant into versioned cases:

```python
case = {
    "id": "rag-auth-001",
    "request": "Add tenant-filtered policy retrieval.",
    "workspace_version": "commit-abc123",
    "rubric": [
        {"name": "authorized_retrieval", "weight": 4},
        {"name": "cross_tenant_blocked", "weight": 4},
        {"name": "citations_returned", "weight": 2},
    ],
}
```

Keep executable checks next to the rubric:

```python
assert ask("Tier B limit", tenant="A").status_code == 200
assert "tenant-B-secret" not in ask("limits", tenant="A").text
assert ask("Tier B limit", tenant="A").json()["citations"]
```

The rubric explains quality; deterministic assertions prove properties that code can verify.

### Small measurable experiment

Collect 10 completed project tasks from your own synthetic learning repository. For each:

1. save the pre-task commit;
2. write a user request;
3. define 3–5 acceptance criteria;
4. add at least one runtime check;
5. ask a coding agent to solve it;
6. provide rubric feedback and allow one revision.

Measure:

- first-pass rubric score;
- post-feedback score;
- regression count;
- human review minutes;
- criteria that lacked executable evidence.

**Success condition:** every score is linked to source or runtime evidence, and the revision fixes named defects without breaking previously passing criteria.

### Beginner interview takeaway

“A useful coding-agent benchmark should reflect real tasks and their original environment, not only public bug-fix datasets. I would save the starting commit, write a requirement-derived rubric, attach executable evidence where possible, and measure first-pass quality plus whether specific feedback produces a verified repair.”

## Five-minute interview recap

- Multi-hop retrieval follows new information discovered in earlier evidence.
- A vector database with metadata links can teach graph-style retrieval before adopting a graph database.
- Relevant context does not imply authority to edit or call a tool.
- Agent roles written in natural language are guidance; typed, authenticated events support enforcement.
- Human approval latency can become the bottleneck in multi-agent systems.
- Evaluate agents on representative tasks with their starting environment.
- A rubric is useful when each score points to source or runtime evidence.
