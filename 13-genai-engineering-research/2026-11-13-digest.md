## 1. Lightfoot: exact deletion for GraphRAG

- **Primary source:** [arXiv:2611.11010](https://arxiv.org/abs/2611.11010)
- **Submitted:** 7 November 2026
- **Area:** RAG lifecycle and deletion
- **Author-reported finding:** after deleting 10% of an 11,402-passage corpus, Lightfoot's graph matched a fresh rebuild of the surviving documents. Indexing was cheaper than the compared GraphRAG systems, but retrieval quality varied by dataset.
- **Evidence boundary:** this is one implementation on public question-answering datasets. Its cost and answer-quality results are not guarantees for enterprise PDFs.

### Core concept and prerequisite

**Prerequisite:** basic RAG retrieves text chunks for a question and puts them in the model prompt. **GraphRAG** additionally stores entities and relationships so a question can follow links across chunks.

Deletion is harder than removing one vector. A deleted policy may have contributed an entity, alias or relationship shared with other documents. Lightfoot attaches chunk-level **provenance**—the source chunk that produced every graph fact—and derives graph state deterministically from those records. Removing a document therefore removes only facts for which no surviving source remains.

**MuleSoft analogy:** this resembles lineage-aware cache invalidation. If three systems contribute to a canonical customer record, deleting one source must remove its contribution without deleting facts still supported by the others.

### Why it matters

Enterprise RAG needs update, retention and right-to-delete behavior. A fast answer system that cannot prove old content disappeared is operationally unsafe. Exact deletion also makes tests possible: delete, rebuild independently, and compare the two indexes.

### Project connection

Add provenance to the document assistant's graph facts:

```python
facts = {
    ("Tier B", "uses_schedule", "TS-7"): {"policy-v3#chunk-12"},
    ("TS-7", "daily_limit", "75000"): {
        "policy-v3#chunk-18",
        "limits-v2#chunk-3",
    },
}

def delete_document(document_id: str) -> None:
    for fact, sources in list(facts.items()):
        remaining = {s for s in sources if not s.startswith(document_id + "#")}
        if remaining:
            facts[fact] = remaining
        else:
            del facts[fact]
```

Deleting `policy-v3` removes the first fact but preserves the limit because `limits-v2` still supports it. In production, perform this transactionally and delete associated chunks and embeddings too.

### Small measurable experiment

Index 30 synthetic documents with five deliberately shared facts. Delete six documents by provenance, then build a fresh index from the remaining 24. Compare sorted nodes, edges, source IDs and retrieval results byte-for-byte.

**Success condition:** zero orphaned sources, zero deleted-document hits, and identical graph facts to the clean rebuild.

### Beginner interview takeaway

“GraphRAG deletion needs provenance at fact level, because one document can contribute many shared nodes and edges. I would make graph records deterministic from source chunks, remove only unsupported facts, and verify deletion against a clean rebuild.”

## 2. CARE-PO: control the tool-call budget without disabling tools

- **Primary source:** [arXiv:2611.12125](https://arxiv.org/abs/2611.12125)
- **Submitted:** 9 November 2026
- **Area:** tool-use efficiency
- **Author-reported finding:** most studied agent trajectories contained removable calls. Five of six reported operating points improved both success and call count on GAIA, but one model size traded success for fewer calls on held-out benchmarks.
- **Evidence boundary:** the method changes model training. The transferable engineering lesson is to measure useful evidence per call and expose a deliberate effort budget.

### Core concept and prerequisite

**Prerequisite:** an agent loop lets a model choose a tool, inspect the result, update its state and choose again. Every call adds money, latency and another failure opportunity.

A blunt “maximum five calls” rule can stop useful research. CARE-PO instead anchors efficiency to task difficulty and discourages calls that gather no evidence. It also supports effort settings so a caller can request a cheaper or more thorough run.

**MuleSoft analogy:** this is similar to API policies with service-level tiers. A routine lookup gets a small orchestration budget; an investigation may call more systems. Both still have ceilings and observability.

### Why it matters

Call count alone is a dangerous optimization target: an agent with zero calls is cheap but uninformed. Production design must preserve task success while reducing duplicated searches, repeated reads and low-value tool calls.

### Project connection

Add a runtime budget before considering model training:

```python
from dataclasses import dataclass

@dataclass
class ToolBudget:
    max_calls: int
    used: int = 0
    evidence_ids: set[str] = None

    def __post_init__(self):
        self.evidence_ids = set()

    def record(self, returned_ids: list[str]) -> None:
        if self.used >= self.max_calls:
            raise RuntimeError("tool budget exhausted")
        self.used += 1
        self.evidence_ids.update(returned_ids)

BUDGETS = {"fast": 2, "standard": 5, "thorough": 9}
```

Store the query fingerprint, tool, latency, result IDs and whether each call added new evidence. In a LangGraph workflow, route an exhausted run to “answer with current evidence” or “request approval,” rather than silently looping.

### Small measurable experiment

Run 20 fixed questions in `standard` mode. Compare the current agent with a rule that blocks an identical query after it returned no new evidence. Measure answer correctness, calls, latency and unique evidence IDs.

**Success condition:** at least 20% fewer calls with no decrease in correctness on the fixed set.

### Beginner interview takeaway

“I would optimize evidence gained per tool call, not call count in isolation. I expose an effort budget, deduplicate repeated calls, keep a hard ceiling, and compare success, latency, cost and unique evidence before changing the default.”

## 3. Do coding agents follow AGENTS.md-style instructions?

- **Primary source:** [arXiv:2611.13709](https://arxiv.org/abs/2611.13709)
- **Submitted:** 10 November 2026
- **Area:** coding-agent governance
- **Finding:** the researchers linked real context-file snapshots to agent-generated commits and converted observable instructions into executable checks. Adherence split between instructions followed consistently and instructions never respected.
- **Evidence boundary:** the abstract does not claim that context files enforce every rule. It supports measuring each instruction and adding enforcement where text is insufficient.

### Core concept and prerequisite

**Prerequisite:** a coding agent receives repository files, tools and instructions. A project context file such as `AGENTS.md` supplies persistent rules for that repository.

Natural-language instructions influence model behavior, but they are not the same as code enforcement. “Do not edit migrations” is a request; a file tool that rejects migration writes is a control. An instruction is **operationalized** when it becomes a check with a clear pass or fail.

**MuleSoft analogy:** an API specification documents permitted operations, while gateway policy enforces authentication, scopes and quotas. Documentation and enforcement solve different parts of the problem.

### Why it matters

Teams often add more prose after an agent makes a mistake. The paper suggests checking whether the instruction is observable, unambiguous and consistently followed before assuming another paragraph will help.

### Project connection

Turn critical rules into executable checks:

```python
from pathlib import Path

PROTECTED = ("config/prod/", "migrations/")
MAX_CHANGED_FILES = 6

def validate_agent_patch(changed_files: list[str]) -> list[str]:
    errors = []
    if len(changed_files) > MAX_CHANGED_FILES:
        errors.append("patch exceeds file-count boundary")
    for path in changed_files:
        if path.startswith(PROTECTED):
            errors.append(f"protected path changed: {path}")
        if Path(path).suffix == ".py" and not path.startswith("tests/"):
            # A real check would map source files to required tests.
            pass
    return errors
```

Keep explanatory guidance in `AGENTS.md`, but place security, artifact boundaries and mandatory validation in the harness or CI.

### Small measurable experiment

Choose ten repository instructions. Label each as (a) automatically measurable, (b) human-reviewable, or (c) vague. Run five small agent tasks and record compliance per instruction. Rewrite the two weakest measurable rules and add enforcement for one high-risk rule.

**Success condition:** 100% blocking of the enforced violation and a visible compliance table rather than a single overall score.

### Beginner interview takeaway

“Context files are valuable project guidance, but I do not treat them as authorization. I translate critical rules into file-tool or CI checks, measure compliance instruction by instruction, and rewrite rules whose pass condition is unclear.”

## 4. FlowPlan: plan and verify code changes at a higher level

- **Primary source:** [arXiv:2611.13241](https://arxiv.org/abs/2611.13241)
- **Submitted:** 9 November 2026
- **Area:** coding-agent cost and verification
- **Author-reported finding:** across six benchmark/model settings, resolution did not change significantly while token use fell in every setting; reported reductions ranged from modest to more than half, depending on model and benchmark.
- **Evidence boundary:** control-flow and data-flow representations suit some code changes better than configuration, UI or cross-service behavior. The result is benchmark-specific.

### Core concept and prerequisite

**Prerequisite:** a **control-flow graph** represents possible execution paths between operations; a **data-flow graph** represents how values are produced and consumed.

FlowPlan asks the agent to locate and describe a repair on this compact representation before editing raw code. After the edit, it rebuilds the graph and compares the actual structural change with the intended change. This can reduce repeated rereading of large files.

**MuleSoft analogy:** before modifying a large flow XML, inspect a simplified dependency diagram, state the intended route change, then compare the generated flow graph after deployment. The map is cheaper to reason over than every line.

### Why it matters

Coding-agent cost often comes from exploration and repeated verification, not only final code generation. A compact, task-relevant representation can save context tokens, but building it adds latency and complexity.

### Project connection

For the FastAPI document assistant, begin with a simple call map:

```python
planned = {
    "add_edges": {("answer", "check_evidence"), ("check_evidence", "generate")},
    "remove_edges": {("answer", "generate")},
}

def verify_plan(before: set[tuple], after: set[tuple], plan: dict) -> bool:
    return (
        plan["add_edges"] <= (after - before)
        and plan["remove_edges"] <= (before - after)
    )
```

This learning example checks that evidence validation was inserted before generation. Real program graphs require language-aware tooling and normal tests remain necessary.

### Small measurable experiment

Give the same three repository tasks to a raw-file agent and a map-first agent. Track input/output tokens, files opened, tests run, wall time and accepted patches.

**Success condition:** at least 25% fewer tokens with the same number of accepted patches; reject the technique if graph construction makes total latency materially worse.

### Beginner interview takeaway

“A coding agent can plan against a compact code map, record the intended structural delta, edit the source, and compare the new map with the plan. I would still run behavioral tests because structural agreement does not prove correct runtime behavior.”

## 5. ReTrace: turn repeated agent work into deterministic workflows

- **Primary source:** [arXiv:2611.14492](https://arxiv.org/abs/2611.14492)
- **Submitted:** 10 November 2026
- **Area:** agent workflows and tool integration
- **Author-reported finding:** on 79 production-platform procedures, compiled workflows reached 93.8% completion versus 96.8% for the agent at 24% lower cost. On two public benchmark settings, latency dropped sharply while some success was initially lost; repairs from labeled failures recovered part or all of the gap.
- **Evidence boundary:** the workflow is learned from an SOP and a few successful traces. It fits repeated, bounded processes better than genuinely novel tasks.

### Core concept and prerequisite

**Prerequisite:** an agent dynamically chooses the next step with an LLM. A deterministic workflow chooses the next step with code and explicit conditions.

ReTrace uses logged agent runs to extract conditions such as “if the retrieved policy is expired, query the archive,” merges them into rules, and compiles those rules into executable workflow code. The LLM helps discover the process; repeated execution no longer needs an LLM planner at every step.

**MuleSoft analogy:** use an intelligent assistant to discover and prototype an integration, then promote the stable path into a governed Mule flow. Keep the agent for exceptions rather than paying it to rediscover the same routing rule on every request.

### Why it matters

This gives a practical answer to “when should I use an agent?” Use one while the process is uncertain or inputs are novel. Compile stable, high-volume decisions into code for predictability, latency, testing and auditability.

### Project connection

Start with explicit rules for the document assistant:

```python
def next_step(state: dict) -> str:
    if not state["documents"]:
        return "retrieve"
    if any(doc["expired"] for doc in state["documents"]):
        return "retrieve_current_version"
    if state["confidence"] < 0.75:
        return "human_review"
    return "answer"
```

Log which rule fired, the source trace that motivated it, and completion outcome. In LangGraph, each return value maps to a conditional edge.

### Small measurable experiment

Collect 30 traces for one repeated policy-answering procedure. Derive rules from 20, test on 10 unseen cases, and compare agent planning with deterministic routing.

Measure completion, wrong transitions, model calls, latency and cost.

**Success condition:** preserve at least 95% of the agent's completion rate while reducing planner calls by at least 50%. Route unmatched conditions back to the agent or a human.

### Beginner interview takeaway

“Agents are useful for discovering variable workflows, but stable repeated decisions should become tested code. I would compile rules from successful traces, validate them on unseen cases, keep provenance and a fallback, and compare completion, latency and cost.”

## Recommended study order and one-week project increment

1. **Instruction checks:** operationalize five rules for the repository and enforce one high-risk boundary.
2. **Tool budget:** add `fast`, `standard` and `thorough` modes plus call telemetry.
3. **Deterministic routing:** replace one repeated planning decision with a tested Python function.
4. **Provenance deletion:** add source IDs to graph facts and compare deletion with a clean rebuild.
5. **Map-first coding experiment:** use it last because it requires code-analysis infrastructure.

### Combined measurable deliverable

Implement a `POST /answer` request with an effort mode and a `DELETE /documents/{id}` endpoint. Demonstrate in automated tests that:

- repeated empty searches do not consume extra calls;
- the standard mode never exceeds five calls;
- deterministic rules route expired evidence to re-retrieval;
- deleting a document leaves no chunk or fact supported only by that document;
- protected files cannot be changed by the coding-agent tool.

This increment connects RAG lifecycle, agent control, tool integration and coding-agent governance without requiring model training.
